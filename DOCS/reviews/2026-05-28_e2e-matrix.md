## FAIL / PARTIAL root causes

### Scenario 5 — categories_multiselect (was FAIL, now PASS — fixed)

Recorded Sports+Drama; replayed `categories=Kids`. Originally the runner
ended with `['sports']`, not `['kids']`, failing the equality assertion.

**Root cause.** For a client-side (no server search) multi-select the
annotator sets `select_strategy="direct"`. The runner reached the target
checkbox via `_locate_via_template(spec.checkbox_template_fp, {"item": item})`,
but no `{item}` template is ever derived for the nested
`checkbox_template_fp` (and the bound value is the boolean `"true"`, not the
item id), so the runner clicked the literal recorded fingerprint
(`...checkbox-sports`) for every target → always Sports.

**Fix (committed).** The direct/scroll reach path now reaches by the
option's **visible LABEL row first** — `_locate_option_row_by_label(spec,
label)` — exactly like the search path (locked design #3), falling back to
the id template only when the label row can't be matched, then to search.
The options are all present client-side, so matching "Kids" by its visible
text finds and clicks the right row regardless of the un-generalisable id
template. Re-replayed `categories=Kids` live → ended with exactly
`['Kids']` (verified via chip read). Regression test:
`tests/agent/test_multiselect_search_reach.py::test_runner_direct_path_reaches_client_side_option_by_label_row`.

Search-strategy pickers (country, scenario 4) already reached by label;
this change unifies the direct path onto the same robust mechanism.

### Scenario 6 — accordion_toggle (was FAIL, now PASS — fixed, commit `dbc57aa`)

Recorded accordion open (aria-expanded false→true). The annotator
misclassified the toggle as a degenerate `set_selection` (empty
`known_options`, `checkbox_template_fp=None`), so replay failed with
`set_selection: no checkbox_template_fp`.

**Root cause.** `_multiselect_prefix()` matched any testid ending in
`-toggle` (regex `-toggle$`), so `accordion-advanced-toggle` was treated as
a multiselect picker `accordion-advanced`. `_detect_set_selection_clusters`
then claimed the toggle click + the following observed `dom_mutation` (the
aria-expanded flip), and the observed event inflated the cluster past the
`len <= 1` "lone toggle" guard, pre-empting `_detect_toggle_state_clusters`.

**Fix (committed).** A `set_selection` cluster now requires at least one
checkbox/item selection event before it is consumed; a bare `-toggle` click
followed only by observed events falls through. Re-annotated → the step is
a plain replayable `click`; replay opens the accordion (verified
`aria-expanded==true`, panel present). Regression test:
`tests/agent/test_set_selection_wi19.py::test_detector_does_not_claim_accordion_toggle`.

**Residual note (not a bug, documented).** It re-annotates to a plain
`click`, not a `toggle_state`, because the grabber did not capture
`target_state_after` for this click (`_detect_toggle_state_clusters`
requires it to know the desired end state). The plain click correctly opens
a closed accordion but is not start-state-idempotent. Capturing
`target_state_after` on toggle clicks is a separate grabber enhancement.

### Scenario 7 — workflow_submit (PARTIAL, no bug — runner safely strict)

Recorded Submit-for-review (C-3001 draft→in_review). Three findings:

1. **Gate works.** Vanilla CLI replay correctly BLOCKED the destructive
   transition at the human gate (no approval in a non-interactive run).
2. **WI-43 works.** With auto-approve, the runner refused the click with
   `error_kind=target_disabled` ("no readiness signal declared") because the
   Submit button is `disabled` during the post-navigate asset GET and the
   annotator emitted no asset-load readiness signal on the navigate step.
   This is the runner being safely strict, not an action-path defect.
3. **Destructive path proven.** With a real readiness pre-wait (button
   enabled) + auto-approve, `_robust_click` fired and D-4002 transitioned
   draft→in_review (verified via the status pill).

**Design gap (documented, not fixed — needs an annotator decision).**
`annotate` should emit a readiness / post-condition wait on a navigate step
that precedes a click on a control gated by an async load, so vanilla CLI
replay doesn't race the GET. Marked PARTIAL because the destructive
action-path itself is proven but the out-of-the-box CLI replay does not
complete without manual readiness/approval.

## Overall verdict

**Proven end-to-end (teach→annotate→replay over CDP, different value
verified):** native-input fill + real save write, native `select_option`,
`depends_on` cascading selects with baselined waits, server-search
multi-select (`set_selection` search strategy), **client-side multi-select
(`set_selection` direct strategy) retargeting** (scenario 5, after the
label-row fix), label-aware equality, and the destructive transition path
(gate + `_robust_click` + state flip).

**Not yet proven / outstanding:**
- `toggle_state` desired-state idempotency is unproven (grabber doesn't
  capture `target_state_after` on the accordion click); the accordion
  replays as a plain click after the fix.
- Destructive CLI replay needs a navigate-readiness signal to avoid racing
  an async load (scenario 7) — annotator design item.

**6 of 7 scenarios PASS** (two after fixes), 1 PARTIAL, 0 FAIL. Test suite:
**520 passed** (`pytest tests/ --ignore=tests/agent/test_groq_live.py`),
518 baseline + 2 new regression tests. Two bugs fixed and committed
(`dbc57aa` accordion mis-classification; client-side retarget label-row
reach). Nothing pushed yet at the time of writing.
