# Second-Opinion Review

## Bottom Line

Your additive path is the right call. A full chunker + cross-skill composition rewrite is not justified yet. The sprint should focus on **making the current trace replay model observable, less timing-fragile, and capable of set/dependency semantics**.

My main pushback: the current plan slightly underestimates the complexity of `expected_signals`, `repeat_for_each`, and L4 vision, and it should move **post-conditions before vision**. Vision without reliable verification is just a more expensive wrong click.

I also checked the repo shape: `SkillRunner` already has L1/L2/L3/L4 concepts, but the UI/session layer does not expose per-step fallback levels; `use_alternate` is currently treated as retry; and `frame_path` is always empty in the grabber, so iframe/shadow support is more aspirational than real.

---

# Recommended Reorder

I would reorder the sprint like this:

1. **Pre-flight + auth gate**
2. **Observability + diagnostic event schema**
3. **Expected signals + network ignore rules**
4. **Per-step post-conditions**
5. **Disambiguation-hint persistence**
6. **`depends_on` enums**
7. **`repeat_for_each` / multi-select set semantics**
8. **Vision L4a**
9. **Known-blocker handlers**

The biggest reorder: **post-conditions before L4a vision**. Vision fallback needs a deterministic way to prove that its proposed action actually achieved the recorded intent.

# Answers to Your Questions

## 1. Order

Mostly right, but I would put **observability and post-condition foundations ahead of expensive recovery**.

Pre-flight first is correct because it removes a hard blocker. But the diagnostics work should not just be a UI panel reading existing logs; the current logs are not rich enough. Add structured per-step events:

- locator attempts tried
- final level used
- ambiguity count
- wait durations by wait kind
- network signal waits
- post-condition result
- heal backend/confidence

Also, fix the current `use_alternate` behavior before calling it a learning loop. Right now it appears to behave like retry, not “click the selected candidate and persist the hint.”

## 2. `expected_signals` Design

Do **not** make it URL-only. Use a hybrid:

```json
{
  "expected_signals": {
    "network": [
      {
        "method": "GET",
        "url_pattern": "/api/states*",
        "status": 200,
        "max_ms": 1500,
        "optional": false
      }
    ],
    "dom": [
      {
        "selector": "[data-testid='state-select'] option",
        "condition": "options_changed",
        "stable_ms": 250
      }
    ]
  }
}
```

Also add portal-level ignore rules:

```yaml
network_ignore:
  - "/api/notifications*"
  - "/events*"
  - kind: "eventsource"
  - kind: "websocket"
```

For GraphQL portals, URL patterns are too coarse. You need request-body hints like `operationName`.

## 3. `repeat_for_each` Detection

Your instinct is right: **deterministic first pass + LLM confirmation**.

But I’d frame multi-select as **set reconciliation**, not just “repeat N clicks.” The runner should know whether the desired behavior is:

- add missing selected items only
- clear existing selection then select exactly target set
- preserve pre-existing selections
- remove extras

A better annotation might be:

```json
{
  "kind": "set_selection",
  "param": "selected_assets",
  "mode": "replace",
  "open_picker_step": "...",
  "item_locator_template": "checkbox-asset-{item}",
  "commit_step": "..."
}
```

`repeat_for_each` is still useful, but multi-select needs target-set semantics.

## 4. Vision-LLM L4a Economics

Your cost estimate is plausible.

Current Anthropic pricing lists Claude Sonnet 4.6 at roughly **$3 / MTok input** and **$15 / MTok output**. Vision docs estimate image tokens as `width * height / 750`, capped around **1568 image tokens** for Sonnet-class models, so a full screenshot is often about **$0.0047 in image input cost** before text prompt/output.

A realistic L4a call:

- screenshot: ~$0.005
- text prompt/context: ~$0.006–$0.015
- structured output: ~$0.003–$0.008

So **$0.01–$0.03/call** is realistic. For 1–2 calls/run, `$0.05/run` is reasonable.

Recommended caps:

- max **1 L4a attempt per failed step**
- max **10–15s latency**
- max **$0.05/call**
- max **$0.25/run**
- never auto-commit destructive actions from vision without post-condition + gate

## 5. Disambiguation-Hint Feature Set

Minimal robust feature set:

- normalized visible text
- accessible name / role
- nearby row or card text
- column labels + cell values if inside a table/grid
- ancestor section/dialog/landmark
- stable attributes: `data-testid`, `id`, `name`, `href`
- relative bbox within container, not absolute page position
- previous/next sibling summaries
- selected/checked/enabled state
- post-action assertion that was satisfied

Also store **negative candidates** from the ambiguity set. “The operator chose row B over rows A/C/D” is more useful than just “row B looked like this.”

## 6. Composition Deferral

You are right to defer full composition.

A hybrid I would allow in this sprint: **span metadata only**, not cross-skill planning. For example:

```json
{
  "span": {
    "kind": "picker_loop",
    "steps": [4, 5, 6, 7],
    "entry_assertion": "...",
    "exit_assertion": "..."
  }
}
```

That gives cleaner internal structure for repeat/dependency handling without committing to a planner rewrite.

Do not build chunker-only now unless real failure data says “large monolithic recordings are the problem.”

## 7. What You May Be Missing

Highest-priority blind spots:

1. **Data exposure to cloud LLMs**  
   Context snapshots and screenshots may contain enterprise content. Add per-portal `allow_external_llm`, redaction, and audit logging before L4 vision.

2. **Iframes and shadow DOM**  
   Current capture records `frame_path: []`; this is not solved yet. Test it explicitly.

3. **Custom controls**  
   React-select, virtualized lists, comboboxes, drag/drop, rich text editors, and custom file uploaders often do not behave like native inputs.

4. **Idempotency / double-submit risk**  
   Retrying after a partial save/apply can duplicate work. Post-conditions and destructive gates need idempotency awareness.

5. **OAuth/SSO popup windows**  
   Auth probing needs to handle new tabs/windows, not just the current page.

6. **GraphQL/SSE/WebSocket portals**  
   URL-only network waits will fail or over-wait. Use operation names, request body fingerprints, and ignore long-lived channels.

7. **Generated post-conditions can overfit**  
   Do not assert arbitrary AX-tree diffs. Prefer small, action-specific assertions.

---

# Final Recommendation

Proceed with the additive sprint, but tighten it into a measurement-first recovery sprint. The success criterion should be: every failed replay produces a classified failure reason, every recovery attempt is visible, and operator corrections persist into future runs. Composition should remain deferred until diagnostics prove that wrong sub-flow selection is the dominant failure class.
