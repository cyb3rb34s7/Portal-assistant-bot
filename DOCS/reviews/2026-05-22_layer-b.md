## Finding 1 — Playwright real-mouse clicks no-op on CDP-attached Chrome (FIXED)

Driving the dedicated system Chrome (v148) over CDP, Playwright's
real-mouse clicks did **not** fire this React app's `onClick` handlers:

- `locator.click()` → no effect (aria-expanded stays false; picker won't open)
- `page.mouse.click(x,y)` at the correct center → no effect
- `locator.dispatch_event('click')` → **works**
- DPR is 1 and `elementFromPoint(center)` resolves to the right element,
  so coordinates are correct — it's specifically the synthesized
  mouse-event path React doesn't pick up over this CDP attachment.

**Why it matters:** the runner clicks via `locator.click()`. On this
Chrome/CDP combo it would silently fail to operate ANY button — a real
robustness gap for operators on newer Chrome.

**Fix (committed `434c327`):** `SkillRunner._robust_click(loc)` — tries the
real `locator.click()` first (keeps hover/focus fidelity), probes for an
effect (element aria-state flip, else a DOM-mutation signal within a short
window), and if nothing changed, retries with `loc.dispatch_event('click')`
and emits a `runner.click_fallback_dispatch` diagnostic. Wired into
`_do_click`, the set_selection reach clicks, and the open/commit toggles.
Unit-tested (mock page): real click first; fallback only on no-effect.
512 tests pass.

## Finding 3 — replay blocked by two issues (OPEN)

Running `run-skill … -p country=zw` failed. Two distinct problems:

### 3a. Annotator emits a stray boolean param (quality bug)
The recorded checkbox click was folded into the set_selection cluster for
`item_labels`, but the param-binding pass ALSO bound it as a separate
required param `multiselect_country_checkbox_ar` (boolean), and mislabeled
the step `fill_multiselect_country_checkbox_ar`. Replay aborts:
`Step 1 needs parameter 'multiselect_country_checkbox_ar'`. The
cluster-consumed events must be excluded from the param-binding pass so a
set_selection step declares ONLY its list param.

### 3b. The id-vs-label tension for label-indexed pickers (design decision)
This is the real architectural question the operator's portal forces:

- The picker's **search is label-indexed**: `/api/countries?q=zw` → `[]`,
  `q=Zimbabwe` → Zimbabwe. (Confirmed; mirrors the real portal.)
- The option **checkbox locator is id-indexed**: `multiselect-country-checkbox-zw`.

So reaching a target needs the **label** (to search) AND the **id** (to
click the templated checkbox). The recording captured both for the
recorded item (`ar`/`Argentina`). But a **replay-time-new target** (`zw`)
supplied through a single id param has no label — the runner types `zw`,
the label-indexed server returns nothing, the option never surfaces.
Supplying the label instead (`Zimbabwe`) fixes the search but breaks the
id-templated checkbox locator (`…-checkbox-Zimbabwe` doesn't exist).

**Recommended resolution (needs your nod — it's a param-convention choice):**
At replay, the multi-select param should carry the **human label(s)** the
operator actually thinks in ("Zimbabwe"), and the runner should:
1. type the label into the search box (already the search path),
2. click the surfaced option **by matching its visible label text** within
   the filtered popover — NOT by the id-templated checkbox — so no id is
   needed up front,
3. read back the resulting chip to satisfy the equality assertion
   (compare against the label, case-insensitive).

This decouples replay from opaque ids entirely and matches how the real
portal works (humans pick "Zimbabwe"; the DOM id `zw` is incidental). The
recorded `item_labels` + checkbox-id-template stay as the fast path for
id-indexed pickers without a search box.

I did NOT implement this blind — it changes the reach contract and the
param convention, and your input on "params are labels, not ids" is the
right gate. The `_robust_click` fix and the record/annotate proof are
committed; this is the next decision.
